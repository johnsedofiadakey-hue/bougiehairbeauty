## 1. What this is

A website + online booking system for **Bougie Hair & Beauty**, a real salon at 41 Crouch Street, Colchester, UK. Business spec: [`bougie-hair-beauty-project-brief.md`](bougie-hair-beauty-project-brief.md) (five departments — Hair braiding/extensions, Wigs/frontals, Lash extensions, Head spa, Nails; 130 services in [`services.json`](services.json)).

Standalone project — own repo, own Firebase project, own (not-yet-created) Stripe account. Originated from a generic template that had a *different* real business's branding baked in; that's been fully stripped (see git history if you need archaeology — not repeated here since it's long resolved).

## 2. Live infrastructure (all real, all working)

- **Firebase project**: `bougiehairbeauty` (Blaze plan, billing enabled).
- **Hosting**: Firebase App Hosting, backend name `bougiehairbeauty`, region `us-central1`. Live URL: `https://bougiehairbeauty--bougiehairbeauty.us-central1.hosted.app`.
- **CI/CD**: GitHub repo `johnsedofiadakey-hue/bougiehairbeauty`, connected to App Hosting — every push to `main` auto-deploys. Confirmed working end-to-end.
- **Auth**: Firebase Authentication has **Phone** and **Email/Password (with Email Link passwordless)** both enabled on this project (they were NOT enabled by default on the fresh project — this bit us once already; if auth mysteriously fails, check Firebase Console → Authentication → Sign-in method first). Authorized domains includes the real App Hosting URL (also not automatic — had to be added manually).
- **Secrets** (Secret Manager, wired into `apphosting.yaml`): `NEXTAUTH_SECRET`, `CRON_SECRET`, `VAPID_PRIVATE_KEY`. All set. `STRIPE_SECRET_KEY`/`BREVO_API_KEY` deliberately **not yet added** (see §5).
- **Cloud Scheduler**: job `send-booking-reminders` (project `bougiehairbeauty`, region `us-central1`), hits `/api/cron/send-reminders` every 10 minutes with `Authorization: Bearer $CRON_SECRET`. Confirmed working via a manual trigger + direct curl test.
- **Data store**: still the single JSON blob in Cloud Storage (`app-state/store.json`) via `src/lib/data-store.ts` — this has not changed architecturally. **Important footgun already hit twice**: `defaultSettings` in `src/lib/default-data.ts` only affects *brand-new* stores. The live store was created before several defaults existed (`logoUrl`, `heroImage`, etc.), so changing a default in code does **not** retroactively update the already-persisted value — `mergeWithDefaults()` in `data-store.ts` always lets persisted data win. If you change a default and it "doesn't show up," patch the live value directly via `PATCH /api/admin/settings` (logged in as admin) rather than assuming the code change was insufficient.
- **`firebase-admin.ts`** now explicitly pins `projectId: process.env.NEXT_PUBLIC_FIREBASE_PROJECT_ID` on `admin.initializeApp()`. Without this, `admin.auth()` silently infers the project from the local machine's ambient `gcloud`/ADC context — in this dev environment that was a *different, unrelated* GCP project, which caused every `generateSignInWithEmailLink()` call to fail with a confusing "sign-in provider disabled" error that had nothing to do with Firebase config. If you ever see that error again despite Email Link being enabled, check this first.

## 3. Customer-facing features built this session

- **Optional email at booking** (`src/app/booking/page.tsx`, `src/app/api/bookings/route.ts`): phone still required, email optional. If given, triggers a **Brevo transactional email** (branded HTML, logo/colors pulled from Settings) with a Firebase-generated magic sign-in link.
- **Reminder emails**: `/api/cron/send-reminders`, fires ~60 min before appointment start. Skipped outright (marked `reminderSkipped: true` at booking time) if the booking itself was made with under 60 minutes of runway — never wastes a send on a reminder that couldn't have fired anyway.
- **Portal login now has two paths**: phone+SMS-OTP (original) and Firebase **email-link (passwordless)** sign-in (new), toggleable independently via `settings.enableEmailLink`. Both land in the same NextAuth `firebaseIdToken` flow in `src/lib/auth.ts`. `/portal/verify` completes sign-in for both the client-triggered flow (cached email, same device) and server-generated links from emails (always re-prompts for email — there's no local cache in that path).
- **Admin notifications, no email cost**: Web Push (VAPID keys generated locally, no external account — see `.env.local` and `apphosting.yaml` for the key pair) + an in-app badge counter on `/admin/appointments`, both wired into `AdminLayoutClient`. Deliberately **not** email, to protect Brevo's send quota for customer-facing mail only.
- **Brevo itself is not yet configured** — `BREVO_API_KEY`/`BREVO_SENDER_EMAIL` are unset, so `src/lib/email.ts` logs a warning and no-ops on every send (mirrors the existing Stripe "simulate if unset" pattern). The booking flow still works fine end-to-end without it. User said they'll provide the Brevo account later — don't chase this until they do.

## 4. Visual redesign — two passes, both against a reference screenshot the user shared

The user shared a screenshot of a "LUXE Salon & Beauty" template and asked for the Bougie site to match its structure/arrangement closely (not a literal asset copy — different photo, different brand colors) while keeping Bougie's own brand identity. This has been iterative:

**Pass 1 (done)**: black top utility bar (address/phone/socials, new `TopBar.tsx`), centered nav + pill CTA (`Navbar.tsx`, now `sticky` not `fixed`, solid white — this matters for §6 below), full-bleed split hero (no rounded frame), 5-department icon row on the homepage services teaser (grouped from the real 23 categories via new `src/lib/departments.ts` — also fixed a real bug where `ServiceCategoryIcon.tsx` only had icons for a different template's categories, so every real Bougie category fell through to a generic sparkle icon; fixed across the homepage, `/booking`, *and* the admin services page since they all share the component), black "About" section, 4-column "Why Choose Us" icon cards, section reorder to match the reference's flow.

**Fonts changed**: Playfair Display (headings) + Poppins (body), replacing the old default-serif + Inter — explicit user request ("something fancy and beautiful for women"), overriding the general CLAUDE.md Satoshi/Inter default, which is fine since a specific in-session request takes precedence over a general standing default.

**Real bugs found and fixed along the way** (worth knowing so they aren't "fixed" again by accident):
- Responsive nav gap: the centered-nav rewrite cramped/overlapped between 768–1024px (tablet/small-laptop). Fixed by moving the desktop-nav breakpoint from `md` to `lg` and bumping `MobileNav.tsx`'s bottom tab bar to cover that range instead (also bumped the `pb-20`/`pb-0` body-padding breakpoints in `page.tsx`/`about/page.tsx` to match).
- Logo not showing: not a code bug — see the "persisted settings win over defaults" footgun in §2. Patched live.
- Mobile back-button visibility: `/booking`, `/portal`, `/portal/verify`, `/login` all had icon-only back arrows with no visible tap-target background on mobile (under the 44px guideline, easy to miss). All four now get a visible circular badge on mobile only (`sm:` reverts to the original text+icon style).
- Booking page felt overwhelming (23 flat categories in one accordion). Added department tabs (same 5-department grouping as the homepage, via the new shared `src/lib/departments.ts`) above the category list — pick a department, see only its categories. Selection/pricing/submission logic untouched.

**Pass 2 (planned, NOT YET STARTED — this is what's next):** the user shared a second reference — an actual photo of a model (smiling, long dark wavy/straight hair, gray background, black top; saved at `public/hero_model_2.jpg`) — and asked for three specific changes:

1. **Hero image treatment**: swap in `hero_model_2.jpg`, and make it feel *embedded/part of* the hero rather than a separate side panel. Specifically: the seam where the solid pink background meets the photo should look like **torn paper** (irregular jagged edge, not a clean rectangle or simple curve) — plan is an inline SVG `clipPath` with a hand-authored jagged path plus a `drop-shadow` filter so the torn edge reads as if the photo has slight physical depth. Also let the photo bleed/overlap into the text column a bit rather than a hard 50/50 grid split, so it reads as one composed scene, not two boxes.
2. **Glassmorphic navbar**: for the glass effect to be visible, the nav needs something behind it to blur — meaning **this reverses part of Pass 1's `Navbar.tsx` change** (currently `sticky`, solid white, pushes the hero down). Plan: nav becomes a floating overlay again (positioned over the top of the hero), styled `bg-white/*-something*/ backdrop-blur-xl border border-white/40` so the pink/photo visibly blurs through it. **Flag this trade-off to the user if it looks off** — it's a deliberate reversal, not an oversight, but overlapping nav + hero content needs care (top hero content needs clearance, or intentionally sits under the translucent nav).
3. **Color rebalance**: user's explicit ask — "branding colors are pink [but] doesn't mean we should over use it... merge it nicely with other colors that complete and make sense... give me your best." Plan: demote pink (`#E6127E`) to an *accent* used only for CTAs/active-states/key highlights, rather than the dominant background/icon/text-accent color it is everywhere right now. Introduce a warm ivory/cream as the new dominant background (replacing pale pink `#F9DCE8` as wallpaper), and a warm gold/champagne as a second accent (ties into the gold jewelry visible in both reference photos and reinforces "Bougie"/luxe positioning) for small details, dividers, and the torn-edge shadow. Espresso brown/near-black stays for headings and the dark About section. **This changes CSS custom properties consumed everywhere via `--color-primary`/`--color-secondary`/`--color-accent`** (see `src/app/layout.tsx`'s inline `<style>` block and `tailwind.config.js`'s `brand` color mapping) — a global palette shift, not a component-local one. Decide the exact hex values thoughtfully (this note intentionally doesn't pre-commit specific hex codes — that's the next agent's/this session's actual design work) and sanity-check contrast (buttons/text still readable) before committing.

**Nothing in Pass 2 has been implemented yet** — the user explicitly asked for this plan + handover doc to exist *before* any code changes, so a fresh session has full context either way. `public/hero_model_2.jpg` is placed and ready to use; that's the only filesystem change made for Pass 2 so far.
